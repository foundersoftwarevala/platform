# Phase 3 Canonical Task Decision

1. **Recommendation: (A) `tm_tasks` should be the eventual canonical task table**, not a declaration that the current mirror is already consistent.
2. `tm_tasks` owns an explicit allowed-transition function and a database trigger that enforces the Task Manager lifecycle ([20260906140000_tm_task_model_and_lifecycle.sql:80](../../supabase/migrations/20260906140000_tm_task_model_and_lifecycle.sql#L80), [20260906140000_tm_task_model_and_lifecycle.sql:112](../../supabase/migrations/20260906140000_tm_task_model_and_lifecycle.sql#L112)).
3. `tm_tasks` writes status changes to `tm_activity` through a database trigger, and `tm_activity` blocks UPDATE and DELETE ([20260906140500_tm_audit_append_only.sql:19](../../supabase/migrations/20260906140500_tm_audit_append_only.sql#L19), [public-schema.sql:43210](../../supabase/schema/public-schema.sql#L43210), [public-schema.sql:43315](../../supabase/schema/public-schema.sql#L43315)).
4. `tm_tasks` also has operator/member-scoped RLS for reads and member updates ([public-schema.sql:60868](../../supabase/schema/public-schema.sql#L60868), [public-schema.sql:60875](../../supabase/schema/public-schema.sql#L60875), [public-schema.sql:60882](../../supabase/schema/public-schema.sql#L60882)).
5. The task-service and Task Manager API already use `tm_tasks` as their read/write source ([task-service.functions.ts:15](../../src/lib/tm/task-service.functions.ts#L15), [api.ts:36](../../src/lib/tm/api.ts#L36)).
6. The existing database bridge explicitly describes `tm_tasks` as the canonical engine, but keeps `developer_tasks` as a second physical table ([20260906120000_tm_developer_bridge.sql:1](../../supabase/migrations/20260906120000_tm_developer_bridge.sql#L1), [20260906120000_tm_developer_bridge.sql:10](../../supabase/migrations/20260906120000_tm_developer_bridge.sql#L10)).
7. `developer_tasks` has no equivalent independent transition-history table/trigger in the reviewed schema; its self-update protection is a separate guard, and the row-scoped UPDATE policy remains ([20261107T230000_developer_tasks_self_update_guard.sql:32](../../supabase/migrations/20261107T230000_developer_tasks_self_update_guard.sql#L32), [public-schema.sql:53711](../../supabase/schema/public-schema.sql#L53711)).
8. Option A is the least disruptive direction because it retains existing Task Manager lifecycle, audit, and RLS mechanisms rather than inventing a third task store; the bridge already links rows with `developer_tasks.tm_task_id` ([public-schema.sql:25601](../../supabase/schema/public-schema.sql#L25601), [public-schema.sql:33152](../../supabase/schema/public-schema.sql#L33152)).
9. **Do not implement the requested migration yet:** `tm_tasks` has no `developer_id` or `manager_id`; `assigned_to` references `tm_members`, while `created_by` also references `tm_members` and is not proven to mean task manager ([public-schema.sql:33152](../../supabase/schema/public-schema.sql#L33152), [public-schema.sql:47754](../../supabase/schema/public-schema.sql#L47754)).
10. Its existing status vocabulary and payment/approval fields do not match the requested seven-state lifecycle or the proposed verified/payment columns; changing those semantics would risk existing tasks and related automation, so Phase 3 remains blocked pending explicit crosswalk and actor/ownership definitions ([public-schema.sql:33152](../../supabase/schema/public-schema.sql#L33152), [20260906140000_tm_task_model_and_lifecycle.sql:80](../../supabase/migrations/20260906140000_tm_task_model_and_lifecycle.sql#L80), [20260906120000_tm_developer_bridge.sql:29](../../supabase/migrations/20260906120000_tm_developer_bridge.sql#L29)).
